### 41. 修复后端部署路径错误
- **问题**：GitHub Actions虽然显示成功，但后端修改角色API未生效
- **根因**：后端SCP步骤的`strip_components: 0`导致`backend/server.js`被复制到服务器的`/var/www/store-progress-manager/backend/backend/server.js`（多了一层backend目录），而pm2运行的是`/var/www/store-progress-manager/backend/server.js`（旧版本）
- **修复**：`strip_components: 0` → `strip_components: 1`，去掉source路径中的`backend/`前缀，使文件正确覆盖到目标位置
- **提交：** 88bb53f → GitHub Actions 自动部署中

### 42. 修复后端端口不匹配导致API不可用（最终根因）
- **问题**：修改角色功能始终不可用，部署后后端API仍不生效
- **根因**：后端server.js默认监听3001端口，但nginx配置`/api/`反向代理到localhost:3002。端口不匹配，导致所有API请求（登录、数据读取等）实际被转发到3002端口的旧后端进程，新部署的后端在3001端口永远收不到请求
- **修复**：
  1. `backend/server.js`：默认端口 `3001` → `3002`
  2. `.github/workflows/deploy.yml`：健康检查端口 `3001` → `3002`
  3. 部署脚本kill 3001/3002/3003端口旧进程，确保新后端能成功启动到3002
- **关键经验**：服务器端调试必须同时检查后端监听端口和nginx反向代理配置，两者必须一致
- **提交：** beac4a1 → GitHub Actions 自动部署中

### 43. 最终修复修改角色API — root进程占用端口（真正根因）
- **问题**：前面所有部署方式（wget、scp、pm2重启）都显示成功，但修改角色API始终返回"Cannot PUT"
- **排查过程**：
  1. 检查各端口API → 3001/3002/3003 都返回 Cannot PUT，说明所有端口都是旧版本
  2. 检查进程 → 发现有两个 **root** 用户运行的旧版后端（pid 17755、18188，5月7日启动）
  3. 检查nginx配置 → `/api/` 代理到 localhost:3002，而root进程恰好占用3002/3003
  4. admin用户启动的新后端被挤到3001，nginx永远优先访问3002的root旧进程
- **根因**：root 旧进程被系统守护程序自动重启，admin用户无权限kill，导致新后端永远无法在3002端口启动
- **修复**：
  1. 用 `github_deploy` SSH密钥连接服务器（`store_backup_key`不可用）
  2. `sudo kill -9 17755 18188` 强制kill root旧进程
  3. 守护程序自动重启时加载了新版本server.js（文件已通过scp覆盖）
  4. 修改角色API立即生效，返回 `{"success":false,"message":"账号不存在"}`（正常业务逻辑）
- **GitHub Actions同步修复**：改回 `scp-action` 部署backend（避免wget超时），`strip_components: 1`
- **关键经验**：服务器有多个后端进程时，必须检查进程所属用户（root vs admin）和端口占用情况，不能只看pm2列表
- **提交：** fda64d5 → GitHub Actions 自动部署中
